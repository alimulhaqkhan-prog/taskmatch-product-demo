## The Problem

Finding a worker is only part of a local-service transaction. After the match, the client and worker may still face:

- different languages or scripts;
- unclear negotiation and scope;
- changing prices or terms;
- materials and travel-cost confusion;
- arrival and approval coordination;
- important commitments disappearing inside ordinary chat history.

TaskMatch is being designed around an additional **coordination intelligence layer**.

## What Makes TaskMatch Different

- **Multilingual + script-aware communication** — translation and transliteration are treated as separate operations.
- **Private TaskMatch AI Adviser** — task-aware private help for the worker; it does not auto-send on the worker's behalf.
- **Contextual agreement controls** — agreement tools appear when useful rather than cluttering every screen.
- **Task BM continuity** — an evolving record of what was proposed, agreed, pending, changed or conflicted.
- **Research-informed coordination intelligence** — founder R&D around continuity, context, functional status and correction-aware reasoning informs future product logic.
- **Dignified client/worker UX** — both sides are treated with equal visual and interaction dignity.

## Product Flow

**Nearby Tasks → Task Details → Discussion → Contextual Agreement → Both Confirm → Task BM**

Agreement-state direction:

- 🟢 **Green:** agreed
- 🟠 **Amber:** required / pending
- 🔴 **Red:** conflict / change
- ⚪ **Grey:** optional / not applicable

## Working Technical Proof

A working technical proof-of-concept has been tested with:

- separate authenticated **Client** and **Worker** accounts;
- the same shared task on both sides;
- persistent message history;
- live message delivery from one physical phone to another without manual refresh.

The demo seed task used **Bathroom Leak / Plumbing / 300 SAR / Arabic / Riyadh test area**.

This is **technical proof-of-concept evidence, not customer traction**.
